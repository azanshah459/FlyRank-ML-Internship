FlyRank Search Intelligence Capstone · CTR Opportunity Scoring

Which visible pages under-capture clicks, and which to review first?

A repeatable, decision-support ranking of content pages that earn search impressions but convert them to clicks below the rate of similarly-positioned peers — and an honest test of whether a model beats a hand-written rule at that job.

01

Abstract

Search Console surfaces many content pages that rank well enough to be seen yet turn impressions into clicks at a lower rate than their position-tier peers, and a content team with limited review time needs to know which of those pages to open first. Using one month of pseudonymised FlyRank Search Console data aggregated to one row per content page (175,304 pages, 47 clients), a page is labelled a CTR opportunity when its March click-through rate sits below the median for its search-position tier and that rate then rises in April. A transparent volume-and-position rule — the Week-4 baseline — is compared against logistic-regression and random-forest models on one split that places every client entirely in train or entirely in test, with an explicit leakage audit and Precision@K as the primary metric. On the held-out test set the transparent rule scored Precision@50 = 0.40, ahead of logistic regression (0.32) and random forest (0.22); the learned models separated the full ranking better (ROC-AUC ≈ 0.99 vs 0.83) but did not improve the top-of-list precision a reviewer actually uses. The deliverable is a ranked review queue of all 157,790 modelled pages with a reason code and an action per page; it is decision support, not evidence that editing any page will raise its traffic, and the recommendation is to keep the rule as the shipping baseline and use the model probability only as a secondary sort key.
02

Introduction & problem statement

A content or SEO reviewer works down a list. Every page opened is time not spent on another, so the order of that list matters. The judgement this project supports is narrow and concrete: a page is already visible in search — it earns impressions — but under-captures clicks relative to pages appearing at similar positions, so it is a candidate for a metadata or content review (title, meta description, snippet alignment with likely query intent).

The project turns that judgement into a repeatable ranked queue built only from observable Search Console signals, and then asks the harder question the Week-5 brief demands: does a learned model actually beat the transparent rule at ordering that queue? It does not act automatically, it does not model or reconstruct Google's ranking system, and it does not claim that a review will recover clicks.

Decision supported Given this month's Search Console performance, which content pages should a reviewer inspect first for a possible click-through problem — and what is the stated reason for each?

Excluded, and why (public-safe)

  • Any client name, domain, URL, or raw query string — public rule; only pseudonymised hash identifiers are used, and no client-identifying value appears on this page.
  • trend_direction, trend_pct, is_declining_label — label-derived fields; using them as inputs would leak the outcome into the model.

  • The baseline rule's own output — kept out of the model's features so the model is not simply re-deriving the rule.
04

Methodology

Assumptions

  • Click-through rate must be read relative to search position, because position is the dominant driver of baseline CTR.
  • Impression volume is a reasonable filter for how much a given CTR gap matters in practice.
  • A real month-over-month CTR rise is a usable observed proxy for "there was an opportunity here" — imperfect, and revisited under Limitations.

Label definition

Position tiers are cut at 1–3, 4–10, 11–20, 21–50, 51+. For each tier the median March ctr_pct is the benchmark. A page is a positive case when both hold: march_low_ctr — its March CTR is below its tier's median; and ctr_improved — its CTR rose from March to April. is_opportunity = march_low_ctr AND ctr_improved, otherwise 0. Observed positive rate 0.68% (1,073 of 157,790).

Baseline — Week-4, transparent

Flag a page when impressions ≥ median(March impressions) (= 178) and ctr_pct < tier median CTR. Reason code HIGH_VOLUME_LOW_CTR, action REVIEW_CTR. Scored on the same test rows as the models.

Validation design

  • Single GroupShuffleSplit, 20% test, fixed seed 42.
  • Grouped on client_hash_id — no client appears on both sides (verified: 0 overlap). Pages from one client share templates and content patterns, so a plain row split would leak that structure and flatter the score.
  • Baseline and both models are evaluated on the identical held-out test rows.

Leakage checks (asserted in the notebook — all pass)

  • No label-derived or outcome-window column appears in the feature list (set() intersection).
  • Identifiers are used only for grouping and for naming ranked rows.
  • The feature window is confined to March — a date assertion guards it.
  • The baseline's own prediction is excluded from the feature matrix.

Metric

Primary: Precision@K for K = 10, 20, 50 (headline K = 50) — it mirrors the real use, where a reviewer works down a short list. Threshold metrics are reported as secondary context only, because the positive class is ~0.4% of the test set and accuracy is dominated by the negatives.

06

Limitations & honest framing

  • Observed and directional. The label is a proxy built from two observed months, not an experiment. A page can show a CTR gap and later rise for reasons unrelated to any review.
  • No causal claim. Nothing here shows that changing a title, meta description, or body text causes more clicks, and nothing here reconstructs Google's ranking behaviour.
  • The model did not earn its complexity. On the decision metric the rule wins; the models' higher ROC-AUC did not translate into top-50 precision. Added complexity is not justified here on the evidence.
  • Class imbalance. 86 positives in the test set — a handful of cases move Precision@K by whole steps. Treat the ordering as guidance, not a calibrated score.
  • Coverage. Only pages with Search Console data and a positive average position are in scope; newer or very-low-volume pages are excluded and cannot be ranked.
  • One window pair. A single decision month and a single outcome month; seasonality and algorithm updates are not separated out.
  • Decision support only. Every output is a prompt for a person to look, with a stated reason — never an automated change.

Ranked recommendations — the action playbook

The queue scores every one of the 157,790 modelled pages and sorts descending:

Score final_score = 100 · ( 0.70 · model_probability + 0.30 · normalized_ctr_gap )
A higher score means review this page sooner — not that a change will pay off. Given the results above, use the model probability only to order pages within a reason-code group; the reason code and the rule come first.

Reproducibility

  • Repository: github.com/azanshah459/FlyRank-ML-Internship
  • Notebooks (work/notebooks/): w02_ml_task_framing.ipynb, w03_data_contract.ipynb, w04_baseline_score.ipynb, w05_model.ipynb, capstone.ipynb
  • Receipts (work/outputs/): capstone_model_results.json is committed; the ranked CSVs (baseline_action_score.csv, capstone_ranked_recommendations.csv) are git-ignored by design and regenerated on every run.
  • Stack: Python · DuckDB over hf:// · scikit-learn · fixed random seed 42
  • Access: a Hugging Face read token is supplied to the notebook as a secret at run time and is never stored in the repository
  • To reproduce: open capstone.ipynb in Colab, add the token as HF_TOKEN in Secrets, then Runtime → Run all

The five notebooks form one chain: task framing → data contract → transparent baseline → modeling lane → capstone. The capstone reuses the baseline's rule, the modeling lane's is_opportunity label, and the same client-grouped split, then adds the ranked queue.
